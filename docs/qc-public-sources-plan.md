# 퀄컴 모뎀 RF SW 공개 자료 수집 계획

기존 `vendor` 레이어(`qc-*`, 18개 노드)는 MIPI RFFE·ASDIV·FBRx·ET/APT·QXDM/FTM/QMI 등 **공개적으로 알려진
업계 개념 수준**으로만 작성되어 있다. 이 문서는 이 레이어를 확장하기 위해 **퀄컴이 공식적으로 공개한 자료**를
추가로 조사·반영하는 계획이다. 아직 실제 수집/스크래핑은 하지 않았다.

## 0. 반드시 지킬 원칙 (이 계획 전체를 관통하는 제약)

이 저장소는 **공개 GitHub 저장소**로 푸시되고 있고, 특정 벤더(퀄컴)를 실명으로 다루는 내용이 들어간다는 점
때문에 일반적인 리서치보다 훨씬 엄격한 기준이 필요하다. (작성자가 해당 회사 재직자인지 여부와 무관하게,
공개 저장소에 벤더 관련 내용을 올릴 때는 항상 이 기준을 적용한다.)

1. **공개적으로 정식 발행된 자료만 쓴다.** 대상: 퀄컴 공식 웹사이트(qualcomm.com), 개발자 문서
   (developer.qualcomm.com), 공개 특허(patents.google.com 등), 보도자료/제품 브리프, 공개 컨퍼런스 발표자료
   (Snapdragon Summit, MWC 발표 슬라이드/영상), 오픈소스 프로젝트에 공개된 인터페이스 문서(리눅스 커널
   `Documentation/devicetree/bindings/net/qcom,*`, `libqmi`/`ModemManager` 공개 문서), 공개 학술 논문/컨퍼런스
   페이퍼(IEEE 등, 퀄컴 소속 저자가 공개 발표한 것).
2. **로그인/NDA/사내 전용 자료는 절대 쓰지 않는다.** 사내 위키, Confluence, JIRA, 사내 전용 SharePoint,
   "Qualcomm Confidential and Proprietary" 워터마크가 있는 문서, 고객사 전용(파트너 포털) 자료는 접근 자체를
   시도하지 않는다.
3. **"우연히 인터넷에서 찾아지는" 것과 "공식으로 공개된 것"은 다르다.** 유출 문서, 비공식 미러, 3rd-party가
   재업로드한 내부 자료로 보이는 콘텐츠는 검색 결과에 나오더라도 배제한다. 판단 기준: 퀄컴이 자사 도메인이나
   공인된 채널(특허청, 표준화 기구, 학술지)을 통해 **의도적으로 공개**했는지 여부.
4. **출처 없는 "알려진 사실"은 근거로 쓰지 않는다.** 이 계획의 결과물로 만들어지는 모든 노드는 반드시 인용된
   공개 URL 하나로 그 내용을 독립적으로 검증할 수 있어야 한다("일반적으로 그렇다고 알려져 있다"는 문장만으로는
   근거가 되지 않는다). 이는 기존 `qc-*` 18개 노드 작성 때도 지켰던 원칙(TODO 2 검증에서 확인됨)과 동일하다.
5. **문장을 그대로 복사하지 않는다.** 마케팅 문구·특허 청구항 등은 요약해 이 프로젝트 톤으로 다시 서술하고,
   `specRef`에 출처를 명시한다(저작권 정책상 원문 재현 금지).
6. **미발표/루머 제품 정보는 배제한다.** 공식 발표 전 로드맵, 벤치마크 유출 등은 다루지 않는다.

이 원칙에 어긋나는 자료가 발견되면 그 항목은 통째로 제외하고, 애매하면 사용자에게 먼저 확인한다.

## 2. 기존 `qc-*` 18개 노드와의 갭 분석

이미 있는 노드(대괄호는 다루는 범위): `qc-rffe-control`[MIPI RFFE 제어], `qc-band-switch-sequence`[밴드 전환],
`qc-asdiv-control`[안테나 스위치 다이버시티], `qc-rf-calibration-data`[캘리브레이션 개념], `qc-fbrx-closed-loop`
[FBRx 폐루프], `qc-et-apt-tracking`[ET/APT], `qc-rfc-config`[RFC 구성], `qc-diag-logging`[DIAG], `qc-qxdm-log-analysis`
[QXDM/QCAT], `qc-ftm-mode`[FTM], `qc-ue-capability-config`[UE Capability 구성], `qc-sar-proximity-control`[SAR/근접],
`qc-thermal-mitigation-policy`[열 완화], `qc-qmi-interface`[QMI] + 관련 증상 노드 4개.

새로 채울 만한 공백(공개 자료로 뒷받침 가능한 것 위주):

- **QMI 서비스 구조 세분화**: 현재 `qc-qmi-interface` 하나뿐 — libqmi 공개 문서를 근거로 NAS(네트워크 접속),
  DMS(디바이스 관리), WDS(데이터 세션) 등 주요 서비스를 구분해 추가할 수 있음.
- **MHI / 전송 계층**: 모뎀-AP 간 고속 데이터 전송에 쓰이는 MHI(Modem Host Interface)가 리눅스 커널에
  공식 문서화되어 있음 — 현재 그래프에 없음.
- **QTM 안테나 모듈 (mmWave)**: 공개 제품 브리프 수준에서 mmWave 안테나 모듈 아키텍처를 다룰 수 있음 —
  현재 `ant-*` 노드들은 3GPP 표준/일반 구현 관점이라, mmWave 특화 내용은 없음.
  단, 정보가 마케팅 자료 수준으로 얕을 가능성이 높아 노드로 만들 실익이 있는지는 자료를 본 뒤 판단.
- **Modem-RF System 통합 아키텍처**: 모뎀+RF 트랜시버+PMIC를 하나의 "시스템"으로 마케팅하는 개념 —
  현재 `qc-*` 노드들이 각 기능 단위로만 쪼개져 있어, 이를 묶어주는 상위 개념 노드가 없음.
- **공개 특허 기반 ASDIV/FBRx 보강**: 지금 두 노드는 이미 정확하지만, 공개 특허의 "발명의 배경" 절을 근거로
  더 구체적인 판단 로직 범주(예: RSSI 임계값 기반 vs 처리량 기반 등 일반적으로 알려진 접근법 분류)를 보강할 수 있음
  — 단, 특정 세대/모델의 실제 알고리즘 파라미터는 다루지 않음(공개 특허도 청구항 이상은 과도한 디테일).

## 3. 수집 프로세스 (기존 도메인 확장과 동일한 틀 + 출처 검증 단계 추가)

1. **후보 URL 확정**: 1절 카테고리별로 실제 접근 가능한 URL을 먼저 확인(로그인 요구 여부, robots.txt 등)하고
   목록화. 로그인이 필요하거나 접근이 막히면 그 출처는 제외.
2. **WebFetch로 내용 확인**: 각 URL의 내용을 가져와 "회사 기밀 워터마크나 배포 제한 문구가 있는지" 먼저 확인.
   있으면 즉시 배제.
3. **개념 추출 + 재서술**: 원문을 복사하지 않고 이 프로젝트 톤(실무 RF 엔지니어가 이해할 수 있는 설명 + "왜
   중요한가")으로 새로 작성. `specRef`에 `"공개 자료 — <출처명>, <URL 또는 문서 식별자>"` 형태로 출처 명시.
4. **중복/연결 확인**: 기존 `qc-*`/`phy-*` 노드와 개념이 겹치면 새 노드를 만들지 않고 관계로 연결.
5. **기밀성 재검토 (TODO 2와 동일한 절차)**: 작성 완료 후, "이 문장이 인용한 공개 URL만으로 검증되는가?"를
   노드별로 재확인. 애매한 항목은 목록으로 남기고 사용자에게 확인받은 뒤 포함 여부 결정.
6. 이후는 기존 방식과 동일: 병합 → id 중복/dangling edge 검사 → 그래프 연결성(BFS) 검증 → 프론트엔드 반영
   (새 타입이 필요하면 검토) → KV 업로드 → `wrangler deploy`.

## 4. 실행 방식 제안

자료 조사(WebFetch/WebSearch로 후보 URL 확인 및 내용 스크리닝)는 규모가 있으니 먼저 **1절 카테고리별로 실제
사용 가능한 출처 목록을 조사하는 단계**부터 진행하고, 그 결과(어떤 URL이 실제로 유효하고 안전한지)를 먼저
보여준 뒤 — 노드 작성 여부를 확정하는 순서를 제안한다. 즉:

- [ ] 1단계: 카테고리별 실제 URL 조사 및 접근성/기밀성 스크리닝 (결과만 보고, 아직 노드 작성 안 함)
- [ ] 2단계: 스크리닝된 자료 중 실제로 새 노드/보강 가치가 있는 항목을 골라 사용자 확인
- [ ] 3단계: 확정된 항목만 노드로 작성 → 병합 → 검증 → 배포

이렇게 나누는 이유는, "자료를 다 모아서 노드까지 다 쓴 다음에" 기밀성 문제가 발견되면 되돌리는 비용이 크기
때문이다 — 자료 조사와 노드 작성 사이에 사람이 확인하는 지점을 하나 두는 편이 안전하다.
